# AGENTS.md

Operating notes for agents working on **CricScore** (`cric-score-overlay`).

## Stack

- Next.js 16 (App Router, Server Actions), React 19, TypeScript
- Firebase: Auth (Google only), Firestore, Storage. Local dev uses the Emulator Suite or a cloud dev project, chosen in `.env.local`
- Tailwind CSS + shadcn/ui primitives
- Vitest + Testing Library (jsdom)
- Dev server on port 3005 (`npm run dev` adds a Cloudflare tunnel; `npm run dev:no-tunnel` without)

## Data layer

- Server code uses `createServerClient()` from `~/lib/firebase/server`; browser code uses `createClient()` / `firebase` from `~/lib/firebase`.
- Queries use the chainable builder in `~/lib/firebase/query-builder.ts` (`from().select().eq().order()...`). Embedded relations are resolved from `<singular>_id` columns or `table_column_fkey` hints.
- Named procedures (`rpc("record_ball", ...)`) are TypeScript functions in `~/lib/firebase/rpc/`. The scoring engine recomputes every innings from the ball log inside a Firestore transaction.
- Collection metadata (columns, defaults, unique constraints, cascades) lives in `~/lib/firebase/schema.ts`. Add a column there and in `types.ts` when the model changes.
- Scorecards live inside `innings` docs (`batting`, `bowling`, `fall_of_wickets`, `partnerships` arrays plus `last_ball` / `last_over_bowler_id` caches); the ball log is one `overs/{inningsId}_{over}` doc per over; `player_matches/{matchId}_{userId}` holds completed-innings figures for career pages (`~/lib/firebase/scorecard.ts`).
- The match document is written only by structural changes (status, innings change, result, settings, toss, scorers), never by a plain delivery. What changes per ball lives on the current innings: the ball `seq` counter (`innings.last_ball_seq`, carried to the next innings; older matches keep it in `matches.last_ball_seq`, so read `seqCounterOf`, the larger of both), the offline-replay memory (`recent_client_actions`: match ids plus the current innings', `appliedActionIdsOf`) and the over / ball position, derived from `total_balls` (`~/lib/match-position`: `matchPositionOf`, `withMatchPosition`; `matches.current_over` / `current_ball` are stale legacy copies). `innings.carried_penalties` caches the fielding-side penalty events the next innings carries, so closing an innings reads no ball log. `scripts/migrate-per-ball-fields.mjs` copied the old fields over (the old ones stay). `from("batting_performances" | "bowling_performances" | "fall_of_wickets" | "partnerships" | "ball_by_ball")` still works read-only via `legacy-rows.ts` (needs an `innings_id` / `match_id` filter, or `user_id` for batting/bowling). Only the scoring engine writes these documents.
- Writes never happen from the browser; `firestore.rules` only allows public reads. Overlay producer commands too: the control room posts them to `POST /api/overlay/command` (`canProduceOverlay`: match admins and streamers), which merges each into `overlay_state/{matchId}` through `sendProducerCommand` (`~/lib/overlay-state`: the `scene` on air, `auto` rules, the lower third `strap`, the event-card `cue`, `last_command_id`; 1 write per command, deleted with the match). The overlay and the control room follow that one doc (1 read on load, 1 per command), so a reloaded OBS source comes back with what is on air and the control room shows "On air" only once the doc names its command. Themes come from `OVERLAY_THEMES` / `resolveOverlayTheme` (`components/overlay/overlay-themes`), never a hard-coded list. Server-action permission checks shared across features live in `~/lib/firebase/permissions` (`canManageTeam`, `isClubAdminOf`).
- Derived copies are maintained on the server, never by callers (schema stage 3, `scripts/migrate-stage3.mjs` backfills them): search keys (`name_lower`/`title_lower`, `search_prefixes`) and roster / membership name snapshots by `derived-fields.ts` on every write; `matches.innings_summary` (a live match's innings in progress is refreshed only with the next structural change: live cards follow `live_state`, the tournament / club / player pages patch it from documents they read anyway, the team page re-reads it, see `live-innings.ts`), `player_career_stats/{userId}` and the leaderboard shards `leaderboards/{scope}_{id}_{k}` (players hashed into `LEADERBOARD_SHARDS` = 8 per scope, `stats.mjs`; pages read all 8, an update touches only the changed players' shards) inside the scoring transactions (`innings-summary.ts`, `stats-sync.ts`); tournament / club / team snapshots on matches by the write hooks. Search with `prefixSearch` (`search.ts`), not `ilike` (which scans). Also derived: `clubs.team_count` (teams write hook, `club-team-count.ts`) and each match's innings-summary totals (`summary_runs`, `summary_wickets`, `best_innings`, `best_innings_runs`: `summaryTotalsOf` in `derive.mjs`, written with every summary by `inningsSummaryPatch`; hidden from `*` and not part of `match_rev`), backfilled by `migrate-club-team-counts` / `migrate-match-summary-totals`.
- No page reads a whole collection. Directory lists are keyset pages of 30 (`~/lib/keyset`, `Pager`, the builder's `keyset()` / `after()`: Firestore's order, ties by id, nulls lowest): players, teams and clubs in `name_lower` order, tournaments latest `start_date` first (undated last); detail pages list the latest 50 matches / first 100 members with a "Show more" link (`ShowMoreLink`, `?matches=` / `?members=`) and, only when a list is cut short, take totals from aggregations: `count()` through the builder (`select("id", { count: "exact", head: true })`), the team record from counts (`teamRecordFromCounts`), club milestones from `rpc("club_milestones")` (`club-milestones.ts`: count / `sum()` / top innings; `DataSource.sum`). The player page lists matches the player has records in plus their teams' live and next 20 fixtures; the match wizard reads only what it can offer (`create/wizard-data.ts`); an organiser's register-team list is read when the dialog opens (`getRegistrableTeams`).
- Deleting a match: `deleteMatch` server action → `rpc("delete_match")` (`rpc/delete-match.ts`). Allowed for the match creator, club admins and the tournament creator (`canDeleteMatch`; co-scorers in `match_admins` may not), after typing the match title. It recomputes the points table without the match, deletes its `overs` / `innings` (batches of 400, no hooks), drops the id from `invitations.scorer_match_ids`, then in one transaction removes its `player_matches` with the career / leaderboard changes, `live_state`, `live_scorecard` and finally the match doc (last, so a retry finishes an interrupted delete). UI: bottom of Match Tools and the match page's ⋯ menu (`DeleteMatchDialog`).
- `npx vitest run src/lib/firebase/read-costs.test.ts` bounds the billed reads of each hot page on the seed and on the seed grown to production size (`__fixtures__/scale.ts`: 1,000 matches, 400 teams, 120 clubs, a club with 250 matches and 300 members), where unbounded lists show; keep new queries indexed (equality + order / limit or `array-contains` + order need an entry in `firestore.indexes.json`; the emulator does not check).
- `src/lib/firebase/match-cost.profile.test.ts` scores a whole T20 through the real server actions and bounds the per-match reads / writes of the scorer, a viewer and the overlay (per collection; run with `--silent=false --reporter=verbose` for the table). It also checks that instant scoring's prediction of every delivery / crease / bowler change equals the state built from the server's reply. Today a delivery costs 5 reads (match, innings, over, `live_state`, `live_scorecard`) + 4 writes (the same without the match), the scorer 6 reads, a co-scorer 3, a match-page viewer 1 (Summary / Scorecard / Stats: the scorecard listener alone), the overlay 1.
- Player profile: `users` also holds the self-described `location`, `playing_role`, `batting_hand`, `bowling_style` (`~/lib/player-profile`: options, validation and the header's detail line; written by `updateProfile` with the name). The statistics tab (`SeasonStatistics`) shows career figures or one calendar-year season computed from the player's `player_matches` records (`~/lib/season-stats`; fielding is career-only).
- `users` is public, so it holds no contact details. Email/phone live in server-only `users_private/{uid}` (`~/lib/firebase/user-private`); look up by exact email there, never return emails to the browser (a user's own email comes from their session).
- Matches carry `team1_snapshot` / `team2_snapshot` ({ id, name, short_name, logo_url }). Match lists select `MATCH_TEAM_COLUMNS` and call `attachMatchTeams` instead of embedding `teams`; the server write hook keeps snapshots fresh when a team's name/short name/logo changes. Embed `teams` only when full team data (rosters) is needed. The home, `/matches` and dashboard lists run `fetchMatchList` (`app/matches/match-list.ts`) on the browser's Firestore client (same reads as the `getMatches` server action, no server request).
- A DLS revision lives on the match (`matches.dls_revision`: `{ innings_number, target_runs, overs }`, written by `updateDlsTarget`, cleared by a target set by hand) next to the innings' `target_runs`: `inningsLimits` gives that innings the revised overs (the engine ends it there), `live_state.dls_overs` carries it while it is the current innings, and the UI counts the chase with `chaseLine` / `inningsOvers` (`~/lib/cricket`), never `overs_per_innings` directly.
- Realtime: viewers listen to the single `live_state/{matchId}` doc (`useLiveState`, `watchDoc`); its `version` is the change signal, and `overs_changed` / `innings_changed` name the documents the change wrote (null `innings_changed`: unknown). No polling and no collection listeners (their first snapshot bills every document). A server action that changes what viewers see must call `refreshLiveState` / `refreshLiveMatchesFor` from `~/lib/firebase/live-sync`. Every live view needs a listener: match cards (`useLiveListMatch`) and the scoring screen for spectators / co-scorers (`useLiveResync`) follow `live_state` too. `watchDoc` re-attaches after a long hidden spell or bfcache restore, and live matches get a stale-listener check (1 server read after 3 min of silence).
- Live match page, zero server requests per ball: Summary / Scorecard / Top performers / Stats follow `live_scorecard/{matchId}` (compact scorecard of every innings, `live-scorecard.ts`; written by the scoring transactions and `writeLiveState`, built on first view by `ensureLiveScorecard`). It carries `live`, a copy of the `live_state` written in the same commit (`stageLiveCopies`, run last in every scoring transaction; no `refs`), so while a spectator page follows the scorecard `useLiveState` drops its own listener and is fed from the copy (1 read per ball, not 2); without a copy (an older doc, an error) it listens to `live_state` again. Every `live_state` write must go through a scoring transaction (`stageLiveState` / `writeLiveState`) so the copy follows; the ball log re-reads only the `overs` docs named by `live_state.overs_changed` (`useMatchBallLogQuery`); `getMatchBallLog` (`rpc("match_ball_log")`, `match-ball-log.ts`) reads a completed innings from its archive `ball_logs/{inningsId}` (every over in one doc, built by the server the first time it is read, in a transaction; ~45 reads a T20 before, 7 now) and the innings in play from its overs. Every scoring transaction that writes an over of an innings already completed, or deletes an innings, drops its archive (`stageBallLogInvalidations`, run last), `delete_match` removes them, and an archive whose innings changed since (`ballLogStamp`) is rebuilt; a script that rewrites a completed innings' overs outside a scoring transaction must delete its `ball_logs` doc; `getMatch` refetches only on status / innings / `live_state.match_rev` changes. The overlay stays on `live_state` per ball (plus `overlay_state`, which only producer commands write, and `live_scorecard` only while a scorecard card is on air); `?delay=N` holds each score change N seconds for streams whose video lags.

## Auth and invites

- Sign-in is Google only and invite-only. `/api/auth/session` (`src/app/api/auth/session/route.ts`) calls `canSignIn` in `~/lib/firebase/rpc/access.ts`: allowed when the account already has a profile, its email is in `ALLOWED_EMAILS` (bootstrap admins; env var locally, Secret Manager secret `allowed-emails` in production), a seeded/placeholder profile has that email, or a pending invite / club invite exists. Refused accounts get a 403 and their new Auth account is deleted.
- The session cookie is `__Host-cric_session` in production (Secure, Path=/, no Domain; plain `cric_session` on http dev servers), named in `~/lib/firebase/session-cookie` (shared with `proxy.ts`). The pre-prefix name is still accepted until 2026-11-05 and cleared at the next sign-in sync. Sign-out sends `Clear-Site-Data: "cache"` (not "storage": it would delete unsent scoring actions), clears the service worker's page cache and the per-match data on the device (`clearScorerData`) except for matches with queued actions, and warns first when actions are still unsent.
- The root layout reads the session cookie per request (`getInitialUser`, `~/lib/firebase/initial-user`: a local signature / expiry check, no Firestore read) and seeds `AuthProvider initialUser`, so a signed-in visitor's first paint is already signed in (`loading` false). Every page is therefore rendered per request. Firebase Auth in the browser still confirms it, or signs the user out when it disagrees. Without a known user, `loading` stays true until Firebase answers: UI that depends on being signed in must reserve its space while `loading` (skeleton), never show Sign in for it.
- Invites send no email: `InviteDialog` / `InviteShare` build a sign-in link message to share on WhatsApp or copy; the match scorers dialog invites new scorers the same way. There is no email/password sign-in, sign-up page or phone sign-in.

## Deploys and migrations

- Production: Firebase project `cricscore-prod-7411`, App Hosting backend `cricscore` (asia-southeast1, `apphosting.yaml`), Firestore in asia-southeast1 (delete protection, PITR, daily backups kept 7 days), domain cricscore.altorstudio.com (Cloudflare DNS, records DNS-only). Never deploy, push or touch the cloud project unless asked.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, tests and build on PRs. App Hosting builds again on its side and replaces `next.config.mjs` with a wrapper that exports only the default config, so nothing may import named exports from it (a test doing so fails the production build's type check while CI passes): helpers it uses live in `src/lib/next-rewrites.mjs`. A merge to `main` deploys Firestore rules + indexes, runs `node scripts/migrate.mjs`, then rolls out that commit on App Hosting. `main` is protected (PR only, required check).
- Monitoring: Cloud Monitoring uptime check on `/api/health`, alerts on downtime and logged errors; browser errors reach the server log via `/api/client-error`, and field Core Web Vitals (LCP, INP, CLS, FCP, TTFB; production only) via `/api/vitals` as INFO entries (`jsonPayload.source="web-vitals"`; a visit's metrics go in one beacon when the page is hidden, `{ metrics: [...] }`, and a single metric is still accepted).
- Security headers are set in `next.config.mjs`: `nosniff`, `Referrer-Policy`, a `Permissions-Policy` switching off unused features (camera, microphone, geolocation, payment, usb, topics; clipboard, Web Share, vibration and the wake lock stay), HSTS in production (`max-age=300` for now: raise to a year once it has run cleanly), and, except on Firebase Auth's `/__/` pages and the overlays themselves, `/overlay/<id>` and `/overlay/channel/<id>` (streaming tools may frame them; control rooms and the stream setup page may not; pattern `FRAME_HEADERS_SOURCE` in `src/lib/next-rewrites.mjs`), `X-Frame-Options: SAMEORIGIN` and a CSP of `object-src 'none'; base-uri 'self'; frame-ancestors 'self'; form-action 'self'`. There is no script-src CSP yet (nonces / Trusted Types need browser testing first). No speculation rules: navigation is client-side, so a prerendered document is never used but still costs a server render and Firestore reads. `src/app/robots.ts` keeps crawlers off pages that cost a render and reads but are not content (overlay, scoring screen, report, search, signed-in areas, `/api`, `/__/`); keep `/matches/<id>/og` crawlable for link previews. Logos and banners are uploaded to a new path each time with `immutable: true` (a year's `Cache-Control`).
- Offline / PWA: `public/sw.js` (hand-written) is registered by `ServiceWorkerRegistrar` only in production on https (never dev or localhost; there it unregisters any worker). Each build installs a new worker (`/sw.js?v=<NEXT_PUBLIC_BUILD_ID>`) with fresh caches; updates wait for the "New version available" toast, which is held back while scoring actions are queued. It caches `/_next/static`, icons and manifest, and `/matches/:id/score` HTML (network-first); it never touches POST / server actions, RSC fetches, `/api`, `/__/*` or other origins. Kill switch: set `"disabled": true` in `public/sw-config.json` and deploy (workers unregister and drop their caches on the next navigation or activation); `NEXT_PUBLIC_SW_DISABLED=true` at build also unregisters from the page.
- Mid-match deploys are safe for queued scoring actions: the offline queue replays through the stable route `POST /api/scoring/replay`, not server actions (whose ids change every build, so a pre-deploy client got "Failed to find Server Action"). Instant scoring sends deliveries, crease and bowler changes through the same route while online; the other online actions stay server actions. Contract in `~/lib/scoring-replay/protocol.ts` (zod schemas in `schemas.ts`): `{ v, matchId, actions: [{ id, type, payload, queuedAt }] }`. To change a payload shape incompatibly, add v2 schemas and keep accepting v1 (old queues outlive deploys); an optional field or a new action type needs no new version. An unknown `v` gets 400 `unsupported_version` and the client keeps its queue.
- Data migrations are idempotent `scripts/migrate-<name>.mjs` scripts (`--project=<id>`, `--dry-run`), listed in order in `scripts/migrate.mjs`, which records applied ones in the `_migrations` collection so each runs once per project. Never auto-run destructive steps (e.g. `migrate-stage2 --delete-old`); do those by hand after verifying.

## Working guidelines

1. Keep changes focused and minimal. Preserve existing behaviour and APIs.
2. Verify what you touch:
   ```bash
   npx vitest run <path/to/test.ts>
   npm run typecheck
   npm run lint
   ```
   `npm run analyze` runs the local static analysis (duplication with jscpd, lint incl. complexity and Firebase rules warnings, import cycles with madge, typecheck, `npm audit --omit=dev`). madge skips type-only imports (`.madgerc`); keep runtime imports acyclic (no lazy `import()` to dodge a cycle).
3. Frontend: responsive and accessible (ARIA, labels linked with `htmlFor`/`id` or `aria-labelledby`, search fields with `autoCorrect="off"`), `text-wrap: balance` for titles, `tabular-nums` for score figures, `content-visibility: auto` with a realistic `contain-intrinsic-size` for long lists (not above the fold), rem font sizes (no `text-[10px]`). Every page has a title: `metadata` (the root template makes it "<title> | CricScore"), a `layout.tsx` for client pages, and on detail pages `generateMetadata` reading the main document through the same React `cache()` loader as the page (no extra read). Tabs use `~/components/ui/tabs` (keyboard and `tabpanel` included; a bar that scrolls fades at the edges with tabs beyond them and keeps the selected tab in view). Reduced motion stops entrance / exit and looping animations (spinners keep turning).
4. Visual style (after Scoreline, see `/design`): scores are the hero, chrome stays light and quiet.
   - No decorative motion (`animate-ping`/`bounce`, glows, sparkles). The only pulse is the small red "Live" dot; skeletons and spinners keep theirs.
   - Icons only when they carry meaning; no Sparkles/Zap/Flame/Crown ornaments or emoji. Stat tiles may carry a small icon beside the label. Captain/keeper are "(c)"/"(wk)".
   - `font-semibold` headings, `font-bold` only for score figures (the design uses semibold for most of them); figures in `font-score` (Outfit) with `tabular-nums`, text in Urbanist; sentence-case labels instead of ALL-CAPS tracked micro-labels (table headers and the "LIVE" chip excepted).
   - Cards float: `bg-card` with `shadow-soft` (a hairline ring, which becomes the border in dark mode); `shadow-float` for the tab bar, menus and dialogs; `shadow-primary` only under the primary button / selected tab. The pink-to-lavender wash (`bg-wash`, via `ScreenWash`) only behind the top of a screen; no other decorative gradients, coloured glows or blur blobs. Colour signals state (live, wicket, boundary, win/loss) and primary actions.
   - Plain copy: no hype, no exclamation marks. The OBS overlay's plain packages (Standard, Light, Team colours, Custom) follow the same rules (no bold ALL-CAPS) but keep its condensed broadcast face (`--font-broadcast`); team short codes are data and stay as-is.
   - Broadcast packages (the owner's direction: overlays that look like real TV packages) may use motion, gradients, condensed caps and bold type the way TV graphics do. They use original artwork and descriptive names ("Night stadium"), never a league's or broadcaster's logos, names or marks.

## Design system

- Tokens live in `globals.css` (`:root` / `.dark`): navy `primary`, lavender `primary-soft`, `hero`, the wash (`--wash-1..3`, `bg-wash`), shadows (`shadow-soft` / `float` / `primary`), state colours (`live`, `success`, `warning`) and deliveries (`four`, `six`, `wicket`, `extra`), all in `tailwind.config.ts`; `--ruby` / `--gold` are aliases for `live` / `warning`. Fonts from the root layout: Urbanist (`--font-sans`), Outfit (`--font-score`, figures), Barlow Condensed (`--font-broadcast`, overlay only, not preloaded).
- Components: `~/components/ds/` (presentational, plain props: buttons, chips, tabs, fields, cards, lists, `ScreenWash` / `ScreenBar` / `Sheet`, `TabBar`, `Carousel`, `ScoreHero`, match cards, scorecard tables, standings, stat tiles, meters). `~/components/ui` primitives follow the same look; Dialog / Select / DropdownMenu / Alert are shared.
- Charts: `~/components/ds/charts` (`WormChart`, `OverBarsChart`, `ChartLegend`): drawn at the container's width, or a fixed `width` scaled like an image (print), team colours `series-1` / `series-2` (a colour-blind-safe pair), hover read-out per over. Partnerships: `PartnershipList`; player of the match: `PlayerAwardCard` (`playerAwardOf` in `~/lib/player-award`).
- Phones (below `md`): no header (the app shell hides `NavigationBar`); the tab bar's More drawer holds what it had: Sign in, or the account (profile, create, invites, install app), the theme and Sign out (`components/layout/drawer-account.tsx`, sign-out and username via `~/lib/hooks/useAccount`). Detail screens (match, player, team, club, tournament) start with `ScreenBar` (round back button, title, actions) and put their tabs and content in `ContentSheet`, the white sheet over the wash. Tabs show names only: no icons, no counts.
- Lists use the shared pieces: a match is `MatchCard` (`components/matches/match-card`: a fixture before the start, scores and the chase or result after, `detail` for a player's figures; it follows `live_state`), a tournament is `TournamentCard` (`components/tournaments/tournament-card`, `actions` for an organiser), teams, squads and players are `ListCard` rows with a `TeamCrest` / `Avatar`, a points table is `PointsTable` (`ds/standings`: links, Q / E marks, adjustments, an admin action). A grid item holding truncated text needs `min-w-0`, or it grows past the screen on phones.
- Match page: Summary is the live panel while an innings is in play (`MatchLivePanel`: crease, bowler, this over from `live_state.this_over_balls` / `this_over_runs`, rates; it reads nothing of its own), otherwise each side as on the share-summary image (`buildExportSummary`), the best batters and bowlers, then key moments. Scorecard uses the report's innings model (`allInnings`) and the ds tables. Top performers ranks `calculateSuperstars`; its "How points work" dialog lists the rules of `rankPlayersByImpact`, so change both together. Partnerships are on the Scorecard only. The engine keeps a match "live" between innings, so the page reads `displayStatusOf` (`innings_break` until the chase's first ball). Head to head sits in Info; the ⋯ menu holds Stream this match (`/matches/[id]/stream`: tool steps for OBS / PRISM / vMix, look, the clean overlay link with a QR code, a test graphic, automatic or manual graphics), the overlay control room (`canProduceOverlay`: scorers and streamers), the DLS calculator (live), Reschedule, a finished match's ball-by-ball data (Cricsheet JSON) and Delete match. The overlay output (`OverlayStage`) draws nothing clickable and no status chips: setup and control live on those two pages.
- Match report (`/matches/[id]/report`): a page (no shell, always light) built from these components; `buildMatchReport` (`~/lib/match-report`) turns the match and its ball log into the model it shows. Each `.report-page` (first innings, then second innings onwards) becomes A4 PDF pages in the browser (`components/report/report-pdf.ts`: html2canvas + jsPDF, pinned with SRI, built after load so "Share PDF" opens the share sheet straight from the tap); "Print" uses the print CSS. The canvas summary image (`match-export-buttons.tsx`, `~/lib/canvas`) uses the same palette.
- Overlay packages (`components/overlay/packages/`): the stage resolves the scene's theme id to a `BroadcastPackage` (`registry.tsx`, names in the pure `manifest.ts` that `resolveOverlayTheme` checks). A package supplies components for any of `OVERLAY_ELEMENTS` (score bug, lower thirds, stings, cards, charts...; props in `types.ts`), its palette (the `--ov-*` variables every component reads, through `OverlayFrame`), its own variables, fonts (`next/font/google` with `preload: false`, applied on the stage root) and motion per element (WAAPI enter / exit / update, `motion.tsx`; `AnimatedNumber` for figures). Elements it leaves out fall back to Standard's (`standard.tsx`). `OverlayElement` draws one element and keeps it mounted while its exit plays; the control room preview honours `prefers-reduced-motion`, the OBS output always animates. `/overlay/gallery?package=&element=&state=&variant=&kind=&bg=` (dev only, like `/design`) draws any element from the demo match at 1920x1080 for screenshots (`layout=bottom|top|compact|broadcast` places the score bug). Look-free pieces every broadcast package shares live in `packages/shared/` (canvas and title-safe anchors, figures derived from the element props, chart series, crest / photo slots, `packageFonts`; tests stub `next/font/google` in `vitest.setup.ts`); `node scripts/overlay-shots.mjs --package <id> [--port 3021] [--out <dir>] [--all]` shoots a package through the gallery with a dev server running and builds `contact-sheet.png`.
- `/design` is the living reference (every token and component, light and dark, composed phone screens). Dev only: its layout calls `notFound()` in production builds.

## Local testing

- `npm run dev:local`: emulators (Auth :9099, Firestore :8088, Storage :9199, UI :4000) + `seed --if-empty` + `dev:no-tunnel` on :3005. Emulator data persists in `firebase/emulator-data` across restarts; `npm run seed` wipes and reloads (Firestore and Auth).
- `npm run dev`: dev server + Cloudflare tunnel (`scripts/dev-tunnel.sh`) for phones; fixed host with `DEV_TUNNEL_NAME` / `DEV_TUNNEL_HOST` in `.env.local`, else a random trycloudflare URL. It registers the host as an Auth authorized domain (`scripts/firebase-auth-domain.mjs`) and skips the tunnel when the emulators are in use.
- Cloud dev project instead of emulators: set `NEXT_PUBLIC_FIREBASE_USE_EMULATOR=false`, the Firebase config and `FIREBASE_SERVICE_ACCOUNT_JSON` in `.env.local`. `npm run seed -- --project=<id>` refuses ids containing "prod".
- Signing in on the emulator: "Sign in with Google" → **Add new account** in the fake picker → a seeded email such as `john.smith@email.com` (`scripts/seed-emulator.mjs`; seeded users have no passwords).
- Environment traps (details in `README.md` → Troubleshooting): leftover service worker on port 3005; stale Turbopack cache after deleting files; `ChunkLoadError` or hangs over the tunnel. For the last two, stop the dev server, `rm -rf .next`, restart. Over the tunnel, `next.config.mjs` serves `/_next/*` with `no-store` in development (Cloudflare otherwise caches dev chunks for 4 hours, and their names do not change with their content: stale code, hydration mismatches), and allows `DEV_TUNNEL_HOST` in `allowedDevOrigins` (Next 16.4 refuses dev resources to other hosts).

## Scoring screen

- `src/app/matches/[id]/score/page.tsx` composes `LiveMatchHUD`, `ScoringPanel` and the dialogs under `score/components/`. Match-level actions live in the Match Tools menu; squads are managed in `SquadManagerDialog`.
- Below 640px the layout is a single column that must fit one phone screen without scrolling: the HUD hides card headers and shows its controls inline (`useMediaQuery`), and the keypad grows to fill the remaining height (`max-sm:flex-1`). Keep new elements out of that column or hide them on phones.
- Undo removes the last ball and reopens the innings/match it closed; the ball log is the source of truth, so never patch totals directly. A recompute (undo, edits, retirements, penalties) keeps the crease / bowler the scorer chose since the last ball when the log leaves that end empty (never someone the log sent off, nor the bowler of the over just ended), and drops batters / bowlers the log does not name and who have nothing recorded (e.g. the batter brought in for an undone wicket).
- Instant scoring (`~/lib/scoring-prediction`, on unless built with `NEXT_PUBLIC_INSTANT_SCORING=false`): a delivery, crease or bowler change, a retirement or penalty / bonus runs to the batting side is queued (`instant: true`) and shown at once, predicted by the engine's own pure functions (`~/lib/firebase/scoring/ball-docs`, shared with `rpc/scoring.ts`) on the stored documents the screen holds (`getScoringState` returns them as `base`; replies and co-scorer reads keep them current). The queue is sent in the background (`flushQueue` in `useScoring`, one flush at a time, retried with backoff); the reply's merged `delta` becomes the confirmed state and the rest of the queue is folded on top (`foldPending`). Undo is instant too (`~/lib/scoring-undo`): the screen keeps, for the recent balls it saw happen (its own, a co-scorer's, a retirement: any change of one ball-log entry), the state just before each, checked at undo time against the ball's `seq` and a fingerprint of the scorecard (so an edit in between makes it wait for the server), and kept on the device across reloads; it shows that state at once and queues the undo (the server's undo restores the undone ball's crease and bowler, i.e. that same state; only the `seq` counter stays). The keypad then says what was removed ("Ball removed: Four · 3.6, Starc to Kohli", "Retirement removed: Kohli, retired hurt") with "Restore ball" for a delivery, until the next action; no toast. Retirements and batting-side penalties are logged as events in the over, built by the same functions on both sides (`newEventBall` with `retirementFields` / `penaltyFields`) and predicted with `eventDocsAfter` (`scoring/event-docs.test.ts` checks it against the server's recompute); a retirement at a full crease names both batters and who retired (`dismissed_player_id`), so the partner stays at their end. Not predicted, so the screen waits for the server: other action types (edits, end of innings, penalty runs to the fielding side), a delivery or event ending the innings, an over document it has not seen, anything `ballDocsAfter` / `eventDocsAfter` returns null for. A refused instant action and everything queued after it go to the dead-letter queue and the screen re-reads; a prediction that differs from the server is reported through `/api/client-error`. Keep engine changes to a delivery's documents inside `ball-docs.ts` / `incremental.ts` so both sides stay one implementation.
- No re-read after a ball or a crease / bowler change: `record_ball`, `set_current_batsmen` and `set_current_bowler` answer (`p_with_delta`) with the documents they committed, and `useScoring` builds the `getScoringState` result from them (`~/lib/scoring-delta`; it re-reads only when they are not enough). A mutation that changes what the screen shows must either answer with a delta or have the hook call `syncFromDb`. A co-scorer follows the other scorer the same way (`useLiveResync` -> `syncFromLive`): it reads the `innings` / current-innings `overs` docs that `live_state` says each change wrote and applies them (`applyLiveResync`), re-reading the whole state only after a structural change or a missed version. Visitors known not to score (signed out, or `is_match_admin` false) are sent to `/matches/<id>` (`isKnownSpectator`).
- Every scoring action the screen sends straight away goes through `POST /api/scoring/replay` (`sendNow` in `useScoring`), never a server action, so a deploy mid-match cannot break it; afterwards the screen shows what the server committed (its documents, or one re-read), with nothing patched in between. Dialogs keep their picks until Confirm (the batter / bowler pickers never change the scoreboard first) and preselect nobody.
- Wagon wheel (`SECTORS` in `~/lib/wagon-wheel-utils`, picker `WagonWheelSelector`, chart `WagonWheel`): drawn as seen from behind the striker, so the batter is at the bottom end, straight hits at the top and a right-hander's off side (cover, point, third man) on the right; every shot line starts at the striker's crease. Shots are stored by zone id (`shot_zone`), so the layout only affects drawing. The picker opens only for runs off the bat (not dots, wides, byes or leg byes). Batting hand is not recorded, so left-handers are drawn like right-handers.
- Retirements are never balls (Law 25.4): Match Tools → Retire, the Wicket dialog's "Retired hurt" / "Retired out" (offered only for a plain wicket, either batter) and the batter dialog's Retire all record `retireBatter`, an event in the over shown as "rh" / "ro" (not numbered, not editable; undo removes it). A batter's Change replaces only someone who has not batted yet (no ball, run or retirement: PlayHQ's rule); for anyone else the dialog offers Retire (leaving the field), since replacing them would leave them "not out" off the crease with their runs, or "Wrong player: replace", a correction (`replaceBatter`, `rpc("replace_batter")`): everything the current innings' ball log has for them goes to a squad player who has not batted, who takes their row and place in the order; the scorecard is recomputed from the log (NV Play's "replace for the entire innings"). A retired-hurt batter named again by the log has resumed (`resumeIfRetiredHurt`, in both engines); brought back but not yet named, a recompute keeps them at the crease unless the log's last entry is what retired them.
- Free hits are a playing condition, not a Law: `matches.free_hit` (null or absent: on, so older matches keep them; switched in Match settings). `nextIsFreeHit` (`score/free-hit.ts`) makes the ball after a no-ball a free hit, carried on through a wide or another no-ball, and the Wicket dialog then offers only run out and obstructing the field. Off: nothing is restricted.
- Runs not off the bat on a no-ball or a wide ride in its `extras`, after the 1-run penalty. A no-ball's `no_ball_runs` ("bye" / "leg_bye"; absent: off the bat, so older balls and queued actions keep their meaning) says they were byes or leg byes (`noBallByesOf` in `scoring/recompute.ts`): the bowler is charged the penalty only, the striker faces the ball but scores none of them, and the innings' extras split them from the no-ball; labels read "nb+2b". The keypad asks under an armed No ball (Off the bat / Byes / Leg byes), as does a run out in the Wicket dialog. Runs ran on a wide (`wideRunsOf`; a wide carrying runs in `runs_scored` is older data) cross the batters when odd, a boundary wide does not.
- Balls faced: every no-ball counts as a ball the striker faced, however its runs came (off the bat, byes, leg byes or none); a wide does not unless `wide_counts_as_ball_faced`. A stand's balls are the balls its two batters faced. `matches.noball_counts_as_ball_faced` false (null or absent: on; in Match settings) leaves no-balls out for formats that do. One rule, `ballFaced` in `scoring/recompute.ts`, serves the engine, the prediction and the match report; the offline engine mirrors it. Figures stored before were brought in line by `scripts/migrate-noball-balls-faced.mjs` (`planNoBallFaced` in `~/lib/firebase/noball-faced`, the engine's own code loaded with jiti).
- Scoreboard: the two batters stay in batting order; tapping one puts them on strike (a radio group, the striker alone marked with "*" and "On strike"); each has its own Change. Dialogs and lists have one scroll area on phones (inner lists grow; search and Confirm stay pinned).
- Offline: actions are queued in localStorage (`~/lib/offline-queue`) and replayed in order, one flusher per match, in batches of 10 to `/api/scoring/replay` (`src/app/api/scoring/replay/`: session cookie, same-origin `Origin`, JSON only, 64 KiB / 20 actions). A request with no reply within `replayTimeoutMs` (and the screen's re-read within `SYNC_TIMEOUT_MS`) counts as unanswered, so a connection that stalls while the phone switches networks cannot hold the queue or the keypad; the action stays queued under its id. It runs each action through the same mutation as the server action, with the queue id as `p_client_action_id`, stops at the first failure and answers `applied` / `duplicate` / `failed` per action, plus the merged `delta` of the applied ones. The duplicate-labelling reads run only when an action is marked `resent` (sent before without a reply); the engine refuses a replay either way. A send with no reply never dead-letters its action. A new queueable action type needs a schema in `schemas.ts` (it fails to compile otherwise), a case in `dispatch.ts`, and engine code that calls `guardClientAction` so a re-sent batch is not applied twice.
- Unsaved actions: an action the server refused, and those queued after it, are kept in the dead-letter queue until reviewed; a lasting "N actions not saved" row opens `UnsavedActionsDialog` (send them again in order under the same ids, or discard). The sync banner offers "Discard it" only for a queue head the server answered with a refusal (`refused`, `refusedHeadAction`), never one that went unanswered (it may yet be applied), and asks first.
- DLS (`~/lib/dls`, the DLS calculator): the Standard Edition, i.e. the ICC's published 2002 resource table for matches without the DLS software (`images.icc-cricket.com/image/upload/prd/g9vlypi15msmrfnhucyx.pdf`, other sources in the file), interpolated per ball, G50 200; not the unpublished Professional Edition, so ICC software targets can differ.

## Streaming (streamers, channels, Stream Deck, sponsors)

- Streamers (`matches.match_streamers`) run a match's overlay graphics but cannot score: `canProduceOverlay` (`~/lib/firebase/permissions`, predicate in `rpc/auth-helpers.ts`, rpc `can_produce_overlay`) is match admins plus streamers; `is_match_admin` stays false for them. Added in the match scorers dialog (`MatchStreamersSection`, actions in `app/matches/streamers.ts`); people not on CricScore get an app invite with `invitations.streamer_match_ids` (rpc `invite_streamer`, accepted in `acceptInvitations`).
- Stream channels (`stream_channels/{id}`, `~/lib/overlay/channels`): one fixed overlay link per club ground or camera (`/overlay/channel/{id}`), or a clubless user's own (`owner_id`). Club admins manage them from the club page's Streaming dialog; producers put a match on one with `ChannelPicker`. The channel page listens to the channel doc (1 read, 1 per switch) and loads the overlay's starting data from `GET /api/overlay/match/{id}` (a stable route: OBS sources outlive deploys).
- Stream Deck / Companion: `POST /api/overlay/remote/{token}/{action}` (GET and HEAD send nothing, so a link preview never fires a graphic) (`remote-actions.ts`). Tokens are `{id}.{secret}`, stored hashed in server-only `producer_tokens/{id}` (`remote-token.ts`, shown once, `RemoteControlPanel`), 5 requests a second per token per instance, never logged. Server code sends producer commands only through `sendProducerCommand` (`~/lib/overlay/commands`), which merges them into `overlay_state` (`~/lib/firebase/overlay-control`) and answers false for a command the overlay does not take (routes answer 400). The batting / bowling buttons put up the scorecard card, partnership the partnership card, next sponsor adds one to `scene.sponsorIndex`.
- Sponsor logos: `sponsors` arrays on clubs and tournaments (`~/lib/overlay/sponsors`), files in Storage `sponsor-logos/` (bytes checked: PNG / JPEG / WebP / script-free SVG, at most 1 MB; cached for a year). `resolveMatchSponsors` picks the tournament's set, else the club's; the control room and the setup page copy its corner sponsors into `overlay_state` after their first command when none were ever set (`useOverlayProducer`). The manager scales raster logos down in the browser (`resizeImageFile`, `LOGO_MAX_PX`; SVG as is). Deleting a match removes its tokens and takes channels showing it off air.
